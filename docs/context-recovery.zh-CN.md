# 本地上下文恢复

`context_recovery` 针对 Codex `app_server` 的明确 `invalid_encrypted_content` 终态错误，可处理恢复旧会话失败、发送输入失败和运行中的回合失败。默认关闭；普通助手文字、其他 400 错误和仍在重试的通知不触发：

```toml
[projects.agent.options]
backend = "app_server"
context_recovery = false
```

后续经部署授权后才可改为开启。`exec` 后端不能开启此选项。必须有可持久化的会话存储，并能确认本机旧执行器和读取协程已经结束；不对无法确认停止的外部 WebSocket 执行器重建上下文。

## 任务如何继承

正常会话沿用已有可见历史和宿主输入记录，**不要求模型定期写总结、状态表或检查点**。故障发生后，程序才整理材料：原任务输入、用户可见历史、工具输入和结果、定时或 IPC 来源，以及当前已知的输入回执。

程序先持久保存一次恢复尝试，确认旧执行器停止，再按旧执行器实际使用的模型、思考档位、工作目录、权限、前导指令、可执行文件和环境创建干净上下文。新旧绑定保存成功后，带入恢复期间收到的最新修改，发送一次续接指令。准备阶段最多 90 秒，同时受原回合剩余时间限制；`/stop`、`/new`、`/switch` 优先，迟到的新执行器会被关闭。`/ps` 补充也会保留，恢复准备或首条输入尚未确认时进入队列。

`/ps` 提交收到同类明确错误时也进入统一恢复，原回合结果已经返回后才收到错误仍可接续；属于旧回合或旧执行器的迟到错误，不会打断已切换的新任务。

新模型会明确知道是在承接原任务，并被要求先核对进度：材料可能不完整，应按原授权主动补查相关规则、文件、成果和作业回执；遵守最新修改、取消和暂停要求；已完成的动作不重做，结果不明的动作先核实，仍不明时只暂停对应部分；已有后台任务继续查收或等待。恢复不会增加部署、访问范围或上游调查授权。

程序能确定输入来源、执行和绑定等事实；任务含义与实际完成程度由模型结合工作区证据核对。缺失材料会标明，不会由程序猜出一个“已经完成”的状态。

每个调用回合单独持有本次恢复状态及其领取的排队输入。历史上成功恢复过，不会改变后续普通失败的排队处理；已领取输入保留原回复目标，直到结果送达或收到失败、取消反馈。保存恢复材料期间收到的新修改会在首次发送前补入，仍受原队列容量和准备期限限制。材料生成、存储等待不占用 Engine 全局锁或交互状态锁。

## 次数、材料与回执

- 同一宿主会话承接链最多自动重建一次。换 native ID、发下一条消息、重启进程、成功回复都不清零；空闲自动换会话不会替换带恢复记录的会话，忙锁自愈也不会打断恢复。显式切回该链已知的祖先 native ID 仍继承次数，目标仍是用户选中的那个 ID。`/new` 建立新的宿主会话。
- 正常输入送达、模型回合完成和业务任务完成分别看待。当前恢复阶段、原输入摘要、新旧 ID、来源和错误保存在 `Session.context_recovery`；`model_turn_completed` 仅表示模型回合完成。
- 会话存储旁的 `context-recovery/<id>/visible-material.json` 保存过滤后证据和准备快照，`continuation.txt` 保存实际续接输入。目录权限 `0700`、文件 `0600`，拒绝材料目录软链接；这些运行材料不应提交到代码仓库。
- 导出使用故障执行器实际 home 环境和工作目录，核对准确原生日志 ID、规范工作目录、唯一文件和非子 Agent 元数据。保留可见 `final_answer`，排除 analysis、reasoning、内部总结、密文和原始 system/developer 对象。原生日志路径只作来源定位，模型使用过滤后的材料。原输入和排队修改还会保留原本由 `inject_sender` 启用的发送人信息，与未改变的正文和摘要分开保存。
- 原生日志单行最多 4 MiB，超长行跳过后仍继续读取；单项最多 256 KiB，全部可见项最多 16 MiB／8192 项，在同一预算内保留开头、最近用户修改和最新证据，防止大量工具输出挤掉最近修改，并标明缺口。首条续接输入最多 96 KiB，优先原输入和最新用户更新；完整可用导出留在材料文件。附件元数据保留名称、类型、大小、数量，当前内存中的附件随新回合提供。
- 重启时发现准备或发送中断，不自动重放；旧执行器退出不明、持久化失败或取消时发送结果仍未知，也会阻止普通路径继续复用。回执写入失败保留已知的模型完成证据，同时保留核对门槛。继续前核对材料、进程、绑定和实际动作回执。

前台输入、连续排队回合和迟到队列补收使用同一准入检查。阻止继续时会显示具体原因、恢复编号、会话快照和材料目录，并提示核对证据后再用 `/new` 建立适当的新上下文。

所有会话快照使用同一保存契约，包括未启用恢复时的普通保存：先写入同目录临时文件并同步，再替换目标，不回退到原地覆盖。Unix 另同步目录；Windows 使用带替换和 write-through 标志的 `MoveFileExW`，不对只读目录句柄调用同步。写入失败会报错。已存在但无法读取、解析的快照会保留并报告存储不可用，不视为首次启动；Engine 启动、工作区输入、Relay 和会话清理命令均拒绝使用这类存储。

定时任务继续原来的那次触发，不重新预约或再触发。提示词回合失败会传回调度器，静默任务也一样；shell 定时任务仍只执行原命令，若经 IPC 投入模型，则按原 IPC 输入承接。

调度器明确标记 `new_per_run` 独立会话。复用现有会话的 timer/cron 仍须通过活跃会话归属检查，不从会话键后缀推断独立性。

IPC 回执只增加独立的 `context_recovery` 字段，原输入及哈希、原目标、送达状态和 ACK 均不改写。当前已受理输入可继续，送达不明的 steer 作为待核对证据；之后仍指向旧 native ID 的事件和 ACK 不会自动改投新会话。通用回调迁移与完整 IPC 重构不在本功能内。

## 验证范围

测试全部使用临时目录、假 Agent 和本机 fake app-server，覆盖三类故障入口、排队消息、晚到修改、停止和切换、退出与写入失败、重启及祖先会话次数、回执先后顺序、定时错误、固定 IPC 目标、历史过滤及材料权限。存储回归覆盖坏快照、并发保存、Relay 拒绝、替换失败及长路径；队列回归覆盖落盘失败后的迟到补收、成功恢复后的普通失败。CUJ A9、A10 从 `ReceiveMessage` 验证用户连续修改任务与恢复期间停止。没有通过真实模型调用或上游探针验证。

英文说明与字段解释见 [Local context recovery](context-recovery.md)。
